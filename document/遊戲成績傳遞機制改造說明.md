## 一、背景與問題

這個專案的「遊戲區」是這樣運作的：

- `front/games.php`：列出所有遊戲，每個遊戲有「開始遊戲」按鈕。
- `front/game-play.php`：個別遊戲頁面，把遊戲用 `<iframe>` 嵌進來，旁邊顯示排行榜。
- `games/{id}/index.html`：實際的遊戲（純前端 HTML/JS）。

每個遊戲玩完後會呼叫一個 `sendResultToParent()` 函式，想把成績傳給「母頁面」。

**問題是：** 這個 `sendResultToParent()` 當初是為了「用 `window.open()` 開新視窗」的情境設計的，依賴 `window.opener`。但現在遊戲改成嵌在 `<iframe>` 裡，這套機制**完全不會運作**——成績根本傳不出來，也就無法儲存、無法更新排行榜。

本文件說明為什麼壞掉，以及如何正確改成 iframe 適用的做法。

## 二、改造前的資料流

```
index.php (#content 區塊)
  └─ loadpage() 用 jQuery $.load() 把 front/game-play.php 載入 #content
       └─ <iframe src="games/{id}/index.html">   ← 遊戲在 iframe 裡面
            └─ 遊戲結束 → sendResultToParent()
                 └─ window.opener.receiveGameResult({...})   ← 問題所在
```

改造前的 `sendResultToParent()`（以 `games/1/index.html` 為例）：

```js
function sendResultToParent(result, timeTaken) {
  if (window.opener) {                      // ← iframe 下永遠是 null，條件不成立
    window.opener.receiveGameResult({
      game: "數字挑戰",
      data: { result: result, time: timeTaken },
    });
    window.close();                          // ← iframe 也不能關閉自己
  } else {
    console.warn("無法傳送結果，請確認是否由主頁面開啟");  // ← 現在只會跑到這
  }
}
```

## 三、三個必須解決的問題

### 問題 1：`window.opener` 在 iframe 下是 `null`

`window.opener` 只有「用 `window.open()` 開出來的新視窗」才會有值，指向開啟它的那個視窗。

但 iframe 不一樣：指向母頁面的是 **`window.parent`**，不是 `window.opener`。

所以原本的 `if (window.opener)` 永遠是 `false`，每次玩完只印出一行警告，什麼都沒送出去。

### 問題 2：`receiveGameResult()` 從來沒有被定義

就算 `window.opener` 有值，母頁面也**沒有**定義 `receiveGameResult()` 這個函式（整個專案搜尋不到）。所以這套設計本來就沒接完。

### 問題 3：根本沒有「寫入分數」的後端 API

改造前每個遊戲只有 `games/{id}/api/pull_score.php`（**讀取**排行榜），`game.json` 也只有 `score.pullUrl`。
**完全沒有把分數寫進資料庫的端點**，所以即使成績傳回來了也存不進去。

## 四、改造後的整體架構

改用瀏覽器標準的 **`postMessage`**（跨視窗/跨框架通訊的正規做法）來取代 `window.opener`：

```
iframe 內的遊戲
   │  玩完 → sendResultToParent()
   │  window.parent.postMessage({ type:"GAME_RESULT", score, display }, "*")
   ▼
game-play.php 的 message 監聽器  window.addEventListener("message", ...)
   │  收到後 $.post 到 pushUrl
   ▼
games/{id}/api/push_score.php
   │  從 $_SESSION 取得玩家名稱 → INSERT 進 scores 資料表
   ▼
寫入成功後，母頁面再呼叫 loadLeaderboard() 重新拉一次排行榜 → 畫面更新
```

**為什麼用 `postMessage` 而不是直接呼叫 `window.parent.函式()`？**

- `postMessage` 是瀏覽器設計來做「視窗之間溝通」的標準 API，不論同源或跨源都能用。
- 不需要依賴母頁面剛好有某個全域函式存在，耦合度低。
- 母頁面用一個 `message` 事件監聽器集中處理，邏輯清楚。

## 五、逐檔修改內容

### 5-1. 五個遊戲 `games/1~5/index.html`

把 `sendResultToParent()` 改成用 `postMessage`，並移除 `window.close()`。
函式參數也從原本的 `(result, 各種格式的字串)` 統一成 `(result, score, display)`：

- `result`：`"完成"` 或 `"失敗"`
- `score`：**越大越好的整數**（換算規則見第六節）
- `display`：給人看的原始字串（例如 `"12.34 秒"`）

改造後（以 `games/1/index.html` 為例）：

```js
function sendResultToParent(result, score, display) {
  // 改用 postMessage 把結果送給母頁面（iframe 機制）
  window.parent.postMessage({
    type: "GAME_RESULT",
    game: "數字挑戰",
    result: result,
    score: Number(score) || 0,
    display: display,
  }, "*");
}
```

> `"*"` 是 `postMessage` 的目標來源（targetOrigin），代表「不限定接收頁面的網域」。開發階段最方便；正式環境建議改成實際網域以提高安全性（見第八節）。

呼叫端也跟著調整，把原始值換算成整數分數再傳，例如數字挑戰成功時：

```js
const score = Math.max(1, Math.round(100000 / parseFloat(timeTaken)));
sendResultToParent("完成", score, timeTaken + " 秒");
```

### 5-2. 母頁面 `front/game-play.php`

做了三件事：

**(1) 把拉排行榜的程式碼抽成 `loadLeaderboard()` 函式**，方便寫入新分數後再呼叫一次刷新。每次重繪前先 `$("#leaderboard").empty()` 清空。

**(2) 新增 `message` 事件監聽器**，接收 iframe 傳回的成績。

注意：因為本頁是用 `$.load()` 反覆載入的，如果每次都 `addEventListener` 會疊加好幾個監聽器、造成同一筆成績被送出多次。解法是把處理函式存在 `window.__onGameResult`，**掛上前先移除舊的**：

```js
// 接收 iframe 內遊戲透過 postMessage 傳回的成績
if (window.__onGameResult) {
  window.removeEventListener("message", window.__onGameResult);
}
window.__onGameResult = function (e) {
  const d = e.data;
  if (!d || d.type !== "GAME_RESULT") return;
  if (d.result !== "完成") return;          // 失敗不記錄
  $.post("<?= $game_setting->score->pushUrl ?>",
    { score: d.score, display: d.display },
    (res) => {
      if (res && res.error) {
        console.warn("分數寫入失敗：", res.error);
        return;
      }
      loadLeaderboard();                     // 寫入成功後刷新排行榜
    }, "json");
};
window.addEventListener("message", window.__onGameResult);

loadLeaderboard();
```

### 5-3. 新增五支 `games/1~5/api/push_score.php`

每支只有 `$game_id` 不同。重點：

- 透過 `include_once "../../../api/db.php"` 取得 `$pdo` 與 session。
- **玩家名稱一律從 `$_SESSION['name']` 取得，不信任前端傳來的名字**（避免冒名）。
- 未登入回傳 HTTP 401。
- 使用 **prepared statement**（預備語句）寫入，防止 SQL injection。

```php
<?php
include_once "../../../api/db.php";   // 取得 $pdo 與 session
header('Content-Type: application/json; charset=utf-8');

$game_id = 1;   // 本資料夾對應的遊戲 id

// 必須登入才能記錄成績
if (empty($_SESSION['login']) || empty($_SESSION['name'])) {
    http_response_code(401);
    echo json_encode(['error' => '尚未登入，無法記錄成績'], JSON_UNESCAPED_UNICODE);
    exit;
}

$name  = $_SESSION['name'];
$score = (int)($_POST['score'] ?? 0);

try {
    $stmt = $pdo->prepare(
        "INSERT INTO scores (game_id, player_name, score) VALUES (?, ?, ?)"
    );
    $stmt->execute([$game_id, $name, $score]);
    echo json_encode(['ok' => true], JSON_UNESCAPED_UNICODE);
} catch (Throwable $e) {
    http_response_code(500);
    echo json_encode(['error' => '分數寫入失敗'], JSON_UNESCAPED_UNICODE);
}
```

### 5-4. 五個 `game.json` 加上 `pushUrl`

讓母頁面不用把寫入路徑寫死在程式裡：

```json
{
  "entry": { "url": "games/1/index.html" },
  "score": {
    "pullUrl": "games/1/api/pull_score.php",
    "pushUrl": "games/1/api/push_score.php",
    "columns": ["玩家名稱", "分數"]
  }
}
```

## 六、分數換算規則

這是這次改造最容易被忽略、卻很重要的一個設計問題。

**問題：** 各遊戲送出的「成績」格式不一致，而且不是純數字，方向也不同：

| 遊戲 | 原始成績 | 方向 |
|------|----------|------|
| 1 數字挑戰 | 秒數，如 `12.34` | 越**小**越好 |
| 2 記憶挑戰 | 秒數 | 越**小**越好 |
| 3 反應力測試 | 平均反應 `850 ms` | 越**小**越好 |
| 4 打地鼠 | `85 分` | 越**大**越好 |
| 5 滑動拼圖 | `20 步 / 30 秒` | 越**小**越好 |

但資料表 `scores.score` 是 `INT`，而且所有 `pull_score.php` 都用 `ORDER BY score DESC`（越大排越前）。
直接存字串會出錯，而且「時間越小越好」跟「分數越大排越前」方向相反。

**解法：** 由**各遊戲自己**把成績換算成「**越大越好的整數**」再送出，母頁面只負責儲存。這樣資料庫端的排序邏輯（一律 `DESC`）對所有遊戲都正確。

採用的換算公式：

| 遊戲 | 換算公式 |
|------|----------|
| 1、2（秒數） | `Math.max(1, Math.round(100000 / 秒數))` |
| 3（毫秒） | `Math.max(1, Math.round(100000 / 平均ms))` |
| 4（分數） | 原值（本來就是越大越好） |
| 5（步數+秒） | `Math.max(1, Math.round(100000 / (步數 + 秒數)))` |

同時保留 `display` 字串（如 `"12.34 秒"`）方便日後顯示原始成績。

## 七、完整流程驗證

1. 學生在 `games.php` 點「開始遊戲」 → `loadpage()` 載入 `game-play.php`。
2. `game-play.php` 載入時：掛上 message 監聽器、呼叫 `loadLeaderboard()` 顯示目前排行榜。
3. iframe 內玩遊戲 → 結束 → `sendResultToParent()` 用 `postMessage` 送出 `{type, score, display}`。
4. 母頁面監聽器收到，確認 `type === "GAME_RESULT"` 且 `result === "完成"` → `$.post` 到 `pushUrl`。
5. `push_score.php` 從 session 取名字、用 prepared statement 寫入 `scores`。
6. 寫入成功 → 母頁面呼叫 `loadLeaderboard()` 重新拉排行榜 → 畫面即時更新。

**語法檢查：** 所有新增/修改的 PHP 檔皆通過 `php -l`（No syntax errors detected）。

## 八、延伸提醒（給進階學生）

1. **`postMessage` 的 `"*"` 安全性**
   目前用 `"*"` 代表不限定接收網域，開發方便但任何頁面都能接收。正式環境應改成實際網域（或用 `location.origin`），並在母頁面監聽器中檢查 `e.origin` 是否可信。

2. **種子資料尺度不同**
   `scores.sql` 裡 game 1/2/3/5 的舊資料是大數值（如 95000），跟新公式（如 `100000 / 秒`）算出的尺度不一樣，新玩家的分數通常會排在舊種子資料之後。這只是展示用假資料的問題，排序邏輯本身已一致正確。要乾淨展示可清掉這些舊種子資料。

3. **舊檔仍有 SQL injection 風險**
   `front/game-play.php`、`api/login.php` 等舊檔是把 `$_GET` / `$_POST` 直接字串拼進 SQL，有注入風險。這次新增的 `push_score.php` 已示範用 prepared statement 的正確做法，建議同學日後把舊檔也一併改寫。
